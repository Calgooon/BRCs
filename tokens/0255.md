# BRC-255: HCT — Compact Tokens and Items with Optional Issuer Countersigning

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment). "HCT" is a working name.

## Abstract

HCT is one output format for fungible tokens and for items, which are deploys with a supply of one. An asset is deployed in one of two modes, fixed for life:

- **Open.** The holder's signature alone moves an output.
- **Countersigned.** Every transfer also needs the issuer's signature, so a transfer the issuer refused is not valid Bitcoin. Custodians can release the asset when the issuer is gone, and it then moves on its holder's signature alone.

The two modes trust different things, and nothing in between. An open asset trusts no one: a recipient checks every hop back to the deploy, and a sender ships only the hops the recipient has not already checked. A countersigned asset trusts its issuer: the issuer checked every transfer before signing it, so a recipient checks one transaction. Nothing in either mode depends on an indexer or an overlay.

The format is built for size. A countersigned transfer with one input, a payment and change is 580 bytes, against 891 for the same transfer under [BRC-253](./0253.md), and an open transfer is 452 bytes (§14).

## Motivation

[BRC-253](./0253.md) writes its countersign clause after a [BRC-162](./0162.md) prefix. That ties a design built on the issuer's signature to another token's encoding, its validity proofs and its roadmap. It also costs bytes: every output repeats a 36-byte token id and up to ten 33-byte keys, and every input carries the holder's public key.

Open tokens have a different cost. A recipient must see every transaction back to the deploy, so a proof grows with each hop, and a consolidation pulls in the history of every input it spends.

HCT keeps what works in BRC-253 and changes three things:

1. **Its own prefix.** A 3-byte marker and a 20-byte asset id replace the BRC-162 prefix.
2. **Smaller clauses.** Holder and issuer are named by public key. The release branch is a hash lock rather than a key set.
3. **Fixed trust per mode.** Open assets are checked to the deploy and trust no one. Countersigned assets trust the issuer, and are checked from one transaction.

## Terms

- **Asset.** A token or an item deployed under this document.
- **Asset id.** `HASH160(deploy txid ‖ index)`, 20 bytes: the txid in internal byte order, then the deploy output's index as one byte. It is written as 40 lowercase hex characters.
- **Issuer key.** A compressed secp256k1 public key that signs the deploy, and in countersigned mode accepts transfers. An asset has one issuer key, or a set of `m` of `n` keys (§9).
- **Holder key.** A fresh BRC-42 child public key per output (§10).
- **Accepted transaction.** A transaction in which every input of a countersigned asset is unlocked on the issuer branch (§7).
- **Beacon.** The output an issuer re-spends to show it is alive, shared by every countersigned asset that names it (§8).
- **Release secret.** A 32-byte value whose `HASH160` every countersigned output of the beacon's assets carries. Revealing it releases them (§8).

## Specification

### 1. Locking scripts

The marker is the three bytes `68 63 74` (`"hct"`). Amounts are minimally encoded script numbers. A deploy, a held output and an authority output are:

```
deploy:     <marker>             <supply> <payload> OP_2DROP OP_DROP <clause>
held:       <marker ‖ asset id>  <amount> OP_2DROP <clause>
authority:  <marker ‖ asset id>  OP_0     OP_2DROP <clause>
```

The first push of a held or authority output is exactly 23 bytes, and a deploy's is exactly 3. BRC-162 starts with a 36-byte push or `OP_0`, so neither format parses as the other. A deploy's `supply` is a positive script number. Every output of an asset carries at least 1 satoshi, and the satoshi has no meaning.

**Open clause:**

```
<holder key> OP_CHECKSIG
```

**Countersigned clause, one issuer key:**

```
<holder key> OP_CHECKSIGVERIFY
OP_IF
  <issuer key> OP_CHECKSIG
OP_ELSE
  OP_HASH160 <HASH160(release secret)> OP_EQUAL
OP_ENDIF
```

**Countersigned clause, a shared issuer set:** the same, with `OP_m <key 1> … <key n> OP_n OP_CHECKMULTISIG` in place of `<issuer key> OP_CHECKSIG`, where `1 ≤ m ≤ n ≤ 5`, `2m > n`, and keys are in the order the deploy lists them.

**Countersigned clause, key-set release:** the same, with `OP_k <release key 1> … <release key j> OP_j OP_CHECKMULTISIG` in place of `OP_HASH160 <HASH160(release secret)> OP_EQUAL`, where `1 ≤ k ≤ j ≤ 5` and no release key is an issuer key. Each custodian generates its own key, so no one has to delete a secret. It costs 33 bytes per release key in every output (§8).

**Unlocking scripts:**

```
open:                        <holder signature>
countersigned, issuer:       <issuer signature> OP_1 <holder signature>
countersigned, shared set:   OP_0 <signature 1> … <signature m> OP_1 <holder signature>
countersigned, released:     <release secret> OP_0 <holder signature>
key-set release:             OP_0 <release signature 1> … <release signature k> OP_0 <holder signature>
```

The holder signs with sighash `ALL | ANYONECANPAY | FORKID` (`0xC1`), or `SINGLE | ANYONECANPAY | FORKID` (`0xC3`) for a sale (BRC-253 §6). An issuer signs with `ALL | FORKID` (`0x41`). The open-mode holder MAY use any sighash type.

A wallet MUST parse a clause exactly and re-encode it. Only the canonical encoding counts.

### 2. Deploy

A deploy transaction writes one or more deploy outputs. The asset id of each one is its own outpoint, hashed as in Terms, so one transaction can deploy up to 256 assets, such as the items of a collection.

The payload is a DAG-CBOR map:

| Key | Type | Meaning |
|---|---|---|
| `v` | uint | `1` |
| `mode` | text | `"open"` or `"countersign"` |
| `kind` | text | `"token"` or `"item"`; absent means `"token"` |
| `iss` | bytes or array of bytes | The issuer identity key, or one per cosigner, 33 bytes each (§3) |
| `m` | uint | The threshold of a shared set; absent means 1 |
| `bcn` | bytes | Countersigned mode: the beacon's first outpoint, 36 bytes (§8) |
| `rel` | bytes | Countersigned mode: `HASH160(release secret)`, 20 bytes; absent with a key-set release |
| `relk` | array of bytes | Key-set release: the release keys, 33 bytes each, with threshold `k` |
| `k` | uint | The key-set release threshold |
| `auth` | bool | `true` makes the deploy output a mint authority (§4) |
| `sym`, `name` | text | Display symbol and name |
| `dec` | uint | Decimal places, at most 18; tokens only |
| `icon` | array | `[media type, bytes]` |
| `ctype`, `c` | text, bytes | An item's media type and content |
| `col` | bytes | An item's collection asset id, 20 bytes (§5) |
| `hdl` | text | The issuer's [BRC-169](../peer-to-peer/0169.md) handle |
| `crit` | array of text | Keys a reader MUST understand; a reader that does not know one MUST refuse the asset |

- An item has `kind` `"item"`, `supply` 1, no `dec` and no `auth`.
- The payload MUST NOT contain a URL. Issuers are reached by identity key.
- The deploy output's clause MUST be the mode's clause, with the issuer keys of §3 and, in countersigned mode, `rel`.
- The deploy is an asset only if the issuer signed it (§3).

A reader holds the deploy transaction once per asset and keeps it only when its txid and index hash to the asset id.

### 3. Issuer keys

The issuer key in a clause is not the identity key itself. It is the BRC-42 child of the identity key named in `iss`, for protocol `[2, "hct issuer"]`, key ID `1` and counterparty `anyone`. Anyone can derive it from `iss`, so the asset names its issuer with no extra signature. A shared set derives one key per entry of `iss`, in order.

A deploy transaction MUST have an input signed `ALL | FORKID` by issuer keys: an input that spends an output locked `<issuer key> OP_CHECKSIG`, or `m` of the set's keys in `OP_CHECKMULTISIG` form. The issuer usually funds the deploy from such a coin. Without that signature, a deploy is not an asset. Anyone could otherwise write someone else's identity key into a payload and circulate an open asset in its name.

### 4. Transfers and minting

For each asset id that a transaction writes or spends, the following rules apply. They are read from the claimed spent scripts in Extended Format.

1. **Closure.** Every output carrying the asset id uses the deploy's clause: the same mode, issuer keys and `rel`, with any holder key. A wallet MUST treat an output with the asset id and another clause as not a holding of the asset.
2. **Conservation.** Amounts on the outputs sum exactly to amounts on the inputs. An input that spends a deploy output counts that deploy's `supply`.
3. **Minting.** A transaction that spends an authority, which is a deploy output with `auth` or an authority output, MAY write more than it spends. It writes at most one authority output, and writing none ends minting.
4. **Items.** An item's outputs total exactly 1.
5. **No conjuring.** Every asset id on an output is on an input, except in the asset's own deploy.

One transaction MAY carry several assets.

### 5. Collections

A collection is an asset whose deploy has `auth`. A member deploy names it with `col` and spends the collection's authority, the deploy output or a later authority output, writing the next authority output. Spending an authority needs the issuer, so a copied payload is no membership. A reader checks membership from the member's deploy transaction. A batch deploy (§2) adds many members in one transaction.

### 6. Proof packages

A recipient receives a **proof package**:

```json
{ "v": 1, "subject": "<txid>", "txs": ["<Extended Format, hex>", "…"], "deploys": ["<raw deploy tx, hex>"] }
```

`txs` holds the subject first, then the ancestors §7 needs, each as Extended Format. `deploys` carries the deploys the recipient does not hold, and MAY be empty. A sender SHOULD omit transactions it has already sent the same recipient, and the recipient MAY answer `{ "t": "need", "txids": [...] }`.

### 7. Validity

A recipient validates the outputs of transaction `T` for asset `A`:

1. It checks `T` against §4, and checks every input of `T` that spends an output of `A` by script validation against its claimed script and satoshis.
2. It stops if `T` is `A`'s deploy, signed by the issuer as §3 requires, or if `A` is countersigned and `T` is an accepted transaction for `A`.
3. Otherwise it validates, in the same way, the transaction behind each input of `T` that spends an output of `A`. Those transactions come from the package or from what it has already validated.

A recipient records every transaction it validated, and later walks stop at them too. It credits an output only when that output's transaction validated. It MUST NOT credit an output of a deploy that pays it directly.

**Open assets** therefore walk every hop back to the deploy and trust no one, not even the issuer, for supply. A sender ships only the hops the recipient has not validated (§6), so a recipient that has seen an asset before receives only the new hops.

**Countersigned assets** stop at the first accepted transaction. The issuer accepts only inputs it accepted earlier (BRC-253 §6), so its signature stands for their history. A live asset's transfer is accepted itself, so its package is one transaction.

After a release, holders countersign with the release branch themselves and nobody checks conservation for them. A transfer with a release-branch input is therefore not accepted, and the walk continues back to the last accepted transaction. Otherwise anyone could write the asset's clause onto a new output with any amount and spend it on the release branch.

**Finality.** An open transfer, like any Bitcoin payment, is final once mined. A recipient MAY credit it on miner acceptance. Countersigned finality is BRC-253's: final against the sender once accepted. The exceptions are shared sets, sender-funded trades and released assets, which are final once mined.

### 8. Beacon and release (countersigned mode)

The beacon is a 1-satoshi output locked:

```
OP_IF <issuer key or set> OP_ELSE OP_HASH160 <rel> OP_EQUAL OP_ENDIF
```

The `<issuer key or set>` part ends in `OP_CHECKSIG` or `OP_CHECKMULTISIG`, as in §1. Every asset naming that beacon in `bcn` MUST have the same issuer keys and `rel`. One beacon serves all of an issuer's assets that share those keys, so an issuer refreshes once, however many assets it has.

The issuer refreshes it per BRC-253 §9: it spends the beacon on the issuer branch into output 0 of a new transaction with the same script, mined at least once every `sil / 2` seconds. `sil` is in the deploy payload of the asset that first named the beacon, and is at least 604800 seconds. Live, retired and lapsed follow BRC-253 §9 with the beacon as the asset's beacon.

**Release.** The custodians reconstruct the release secret and spend the beacon on its release branch, writing no next beacon. That spend is the release, and its unlocking script publishes the secret. After it, any holder spends on the release branch with the secret and its own signature, with no issuer: the assets are owner-only. A retiring issuer MAY release itself.

The issuer generates the secret at deploy and splits it among custodians with a `k`-of-`j` threshold scheme, such as Shamir sharing with Feldman commitments so each custodian can check its share. It then deletes the secret. The split is off chain and outside this document. Custodians MUST NOT release a live asset.

**Key-set release.** An asset deployed with `relk` releases as BRC-253 §9 does: `k` custodians spend the beacon on its release branch and disclose their private keys in `OP_FALSE OP_RETURN "hct release" <beacon outpoint> <private key 1> … <private key k>`. The beacon is then `OP_IF <issuer key or set> OP_ELSE OP_k <release keys> OP_j OP_CHECKMULTISIG OP_ENDIF`. Custodians could spend a live asset's output on that branch without publishing, so a recipient credits a key-set release-branch input only once that disclosure is mined, as BRC-253 §11 step 6 requires.

**Release-branch inputs.** The secret is public the moment any release-branch spend is broadcast, so a release cannot happen in private. A recipient still credits a release-branch input only once it has seen the beacon's release spend mined. An issuer-branch input is final under §7.

### 9. Countersigned acceptance

Acceptance follows BRC-253 §4 to §8 and §10, with these changes:

- Outputs and clauses are §1's, and unlocking scripts are §1's. Before acceptance, a holder's half is `<holder signature>` alone. The acceptor completes `<issuer signature> OP_1 <holder signature>`.
- An acceptor's fee coins SHOULD be locked `<issuer key> OP_CHECKSIG`. Such a fee input spends in 114 bytes, against 148 for P2PKH.
- Linkage in a request entry is for protocol `[2, "hct holder"]` (§10).
- Messages go to box `hct`.
- Resolution is §7. An accepted transfer stops the walk, so the recipient needs only the accepted transaction and any deploy it lacks.
- Release follows §8, not BRC-253's key disclosure.

### 10. Holder keys

A holder key is the BRC-42 child for protocol `[2, "hct holder"]`, key ID `<derivation prefix> <derivation suffix>`, with the holder's identity key as counterparty, or `self` for an output the sender keeps. The prefix is fresh per transfer and the suffix per output. No two outputs share a holder key, so the chain does not link a holder's outputs to each other or to its identity.

A delivery carries the remittance of the recipient's outputs:

```json
{ "v": 1, "t": "transfer", "asset": "<asset id>", "senderIdentityKey": "<66 hex>", "outputs": [{ "vout": 0, "derivationPrefix": "…", "derivationSuffix": "…" }], "proof": <§6 package> }
```

It is sealed per BRC-78 to the recipient's box `hct` or sent on a BRC-246 channel. A recipient acknowledges it only after it filed the outputs or found the transfer invalid.

### 11. Filing

Two filing names: `hct` for resolved outputs of tokens and `hcti` for items, in either mode. After BRC-46 normalization, conforming use MUST be exactly these.

- Tag `<filing>:<assetId>` MUST be present. Tag `col:<collectionId>` marks a member whose membership checked out. Tag `hct:auth` marks an authority, which never counts in a balance. Each output carries a BRC-164 `id:<key>` tag.
- `customInstructions`, when present, is a UTF-8 JSON object holding `asset`, `kind`, `mode`, `amt`, `sym`, `dec`, `name` and `col` when known. It also holds `derivationPrefix`, `derivationSuffix` and `senderIdentityKey`, which are the only way back to the holder key. A wallet MUST keep them and include them in its history backup.

### 12. Application access

`hct` and `hcti` are BRC-99 permission schemes, registered per BRC-123, Category 1 (Asset):

| Capability | Wire |
|---|---|
| View all | `listOutputs` basket `p hct all` / `p hcti all` |
| View by asset | `p hct asset` / `p hcti asset` with `<filing>:<assetId>` tags |
| View by collection | `p hcti collection` with `col:<collectionId>` tags |
| Look up a row | `p hct id` / `p hcti id` with `id:<key>` tags |
| Spend, open mode | `createAction` label `p hct input id <key>` / `p hcti input id <key>` |

- A wallet MUST refuse any other scope, a filtered scope without a matching tag, and any request that names a filing directly.
- A countersigned output is spent only through the wallet, which runs §9 itself. An application never receives the holder's signature and never addresses the acceptor.
- Payment, auto-pay and other schemes' grants MUST NOT cover these views or sends.

### 13. Reissuing assets from other formats (informative)

An issuer moving an asset off another token format deploys it under HCT. Each holder then sends its old outputs to the issuer with a `{ "t": "convert" }` request in box `hct`. The issuer pays the same amount in the new asset and burns or keeps what it received. A wallet MAY show old outputs read-only until they are converted. Nothing in this document reads another format.

### 14. Efficiency (informative)

The table measures one transfer: one asset input, a recipient output and change, and one funding input. Signatures are counted at 72 bytes. "Output life" is the bytes an output adds when created plus when spent.

| | Lock | Unlock | Transfer | Output life |
|---|---|---|---|---|
| BRC-253, 1-of-2 issuer, 2-of-3 release | 246 | 182 | 891 | 478 |
| HCT countersigned, one issuer key, P2PK fee coin | 125 | 147 | 580 | 322 |
| BRC-162 with P2PKH | 67 | 107 | 492 | 224 |
| HCT open | 64 | 73 | 452 | 187 |

The countersigned saving comes from:

- a 23-byte prefix instead of 39;
- a holder key in the lock instead of a 20-byte hash with the public key in every unlock;
- one issuer key instead of a key set;
- a 20-byte hash lock instead of three release keys;
- a P2PK fee coin.

Beacons also scale per issuer rather than per asset. A countersigned proof is one transaction, about 0.8 KB in Extended Format. An open proof holds every hop the recipient has not already validated, about 0.5 KB per hop, so a first receipt of an old, busy asset is the largest case.

## Security considerations

- **Issuer trust.** Only countersigned assets trust the issuer. A stolen issuer key can accept forged outputs or accept a spend twice. That is the trust BRC-253 already asks for. A shared set (`m ≥ 2`, `2m > n`) means one stolen key is not enough. A stolen issuer key cannot add supply to an open asset: it can only sign deploys.
- **Open mode without the issuer.** An open asset never needs its issuer after the deploy.
- **Release.** Revealing the secret releases every asset sharing its beacon at once. A release cannot be private, because the secret is on chain at its first use. Custodians that release early end freezes early, but move no output. Every spend still needs the holder.
- **Trusted dealer.** The issuer creates the release secret and must delete it after splitting it. An issuer that kept it can release early. An asset that cannot accept that uses a key-set release, where each custodian makes its own key, at the cost in §14.
- **Extended Format claims.** Each holder signature and countersignature commits to its own input's script and satoshis. False claims fail script validation, or fail on chain, where an invalid ancestor makes every descendant unmineable. A recipient credits only per §7 and the finality rule.
- **Deploy forgery.** A deploy not signed per §3 is no asset. Payload data never names an issuer by itself.
- **Hash-based id.** The asset id is a 160-bit hash. Taking over an existing asset's id needs a second preimage. A collision only lets someone deploy two of their own assets that share an id, and a reader holding both deploys MUST refuse both.
- **Privacy.** Holder keys are fresh children. The issuer of a countersigned asset sees every transfer and the identity behind each output, as BRC-253 intends.

## Rationale

**No middle mode.** An open asset that trusted the issuer for short proofs would carry the issuer's risk without the issuer's control. An asset that needs short proofs and accepts issuer trust is a countersigned asset, and every other asset is checked to its deploy.

**Public keys in the lock.** A hash with the key in every unlock costs more over an output's life. Holder keys are fresh children either way, so naming them reveals nothing.

**A hash lock for release.** A key set would cost 33 bytes per key in every output, plus `k` signatures per release-branch spend. A hash lock costs 21 bytes and a 32-byte preimage, and it makes every release public by construction.

**A derived issuer key.** Deriving the clause key from `iss` with counterparty `anyone` binds the asset to an identity with no signature in the payload. The identity key itself never signs automatically.

**A hashed asset id.** It saves 16 bytes on every output. A recipient needs the deploy once anyway, for its clause and metadata.

## Open questions

1. **Name.** "HCT", the marker, the filing names and the protocol IDs are working names. A rename changes no rule.
2. **Branch byte.** `<issuer key> OP_CHECKSIG OP_NOTIF OP_HASH160 <rel> OP_EQUALVERIFY OP_ENDIF OP_1` saves the `OP_1` branch push in each issuer-branch unlock, if every miner's clean-stack and NULLFAIL policy accepts it.
3. **Zero-satoshi outputs.** If miners relay asset outputs of 0 satoshis, the carrier satoshi can go.
4. **Cross-issuer swaps.** These remain open as in BRC-253.

## Test script

[`media/0255/hct.mjs`](./media/0255/hct.mjs) runs §1's clauses through `@bsv/sdk`'s interpreter. It checks that a countersigned output spends on the issuer branch and on the release branch with the secret, and that an open output spends with its holder's signature.

It also checks that each of these fails:

- the holder without the issuer;
- a wrong secret;
- the secret without the holder;
- the issuer signing in the holder's place;
- a stranger spending an open output.

It checks that anyone can derive §3's issuer key from the identity key, and it prints the lock sizes used in §14. Run `npm install && npm test` in that directory.
