# BRC-252: Short Proofs for Bitcoin Native Tokens

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

A Bitcoin Native Token (BNT) recipient checks every hop back to the deploy (draft BRC-251, [#320](https://github.com/bsv-blockchain/BRCs/pull/320), test 2). Draft BRC-255 ([#335](https://github.com/bsv-blockchain/BRCs/pull/335)) defines that walk and the proof package that carries it. This document keeps the package short as an asset trades. It changes nothing about when an output is valid, and keeps every BNT test: the evidence is still transactions named by txid, and nothing here lets a signer, host or overlay decide validity.

It adds four rules to BRC-255 §6 and §7: any party may serve a transaction by txid; a sender may leave out history its recipient has probably validated; a sender chooses the inputs that leave the least history to send; and a shorter proof counts only when the recipient can check it with no one trusted.

The same rules apply to the walk of a released Issuer-Permissioned Token (IPT) under draft BRC-253 ([#333](https://github.com/bsv-blockchain/BRCs/pull/333)) §11, which uses the same package and also stops at accepted transactions.

## Specification

### 1. A transaction is named by its txid

Any party MAY store or serve a transaction of an asset's history: the wallet, another device of the same vault, the counterparty, or a public host. The recipient MUST accept a served transaction only when it hashes to the txid it asked for. A host that refuses a txid delays the walk. It cannot put a different transaction in its place.

A served transaction is still validated under BRC-255 §7, including the check of each input's claimed script and satoshis against the transaction behind it (BRC-255 §6). A wallet MAY keep one cache of transactions, shared across assets, payments and its own devices. Copying a transaction to another device copies bytes. That device still hashes and validates it.

### 2. Leave out history the recipient has probably validated

A wallet's **frontier** for an asset is the set of transactions of that asset it validated and recorded (BRC-255 §7).

A sender cannot see a recipient's frontier. A BRC-33 acknowledgement deletes the message from the recipient's box and tells the sender nothing. What the sender does see is its own delivery: the recipient's box accepted the BRC-255 §8 delivery and the package it carried.

When the recipient's box accepts a delivery, the sender MAY record that recipient as probably holding every transaction of that package. The record is a guess about what a later package may omit, and nothing more. The recipient may not have read the message yet, may have refused it, or may have lost its records since. The record is not a validation for the sender, and the recipient cannot use it as its own. A wrong guess costs the recipient a fetch, never a wrong verdict.

To build a package for a recipient, the sender walks the asset's inputs back from the subject, as BRC-255 §7 step 3 does. It includes each transaction until every branch reaches the deploy, a transaction it has recorded for that recipient, or, for an IPT, an accepted transaction (BRC-253 §11). It omits everything behind those points. With no record for the recipient, the package carries the full walk.

The recipient walks as BRC-255 §7 says. When it reaches an input whose transaction is neither in the package nor recorded, it takes it from its cache, asks the sender with `{ "t": "need", "txids": [...] }` (BRC-255 §6), or fetches it by txid, and validates it. A fetch that fails leaves the output uncredited. Omitting a transaction never makes an output valid.

Because the sender records on delivery, not on validation, a later delivery can arrive while the one it relies on is still unread. A recipient SHOULD process queued deliveries in the order its box returns them, and MAY take a missing transaction from any other message it holds, under §1.

### 3. Spend the inputs that leave the least history

When more than one set of resolved inputs covers the amount, the sender SHOULD choose the set that minimizes the transactions §2 includes for that recipient. Ties SHOULD go to the inputs this wallet validated most recently.

The choice does not change validity. A payment that spends an older branch is still valid, and the recipient walks whatever arrives.

### 4. A shorter proof counts only when the recipient can check it

A compressed proof claims that a BRC-255 §7 walk already succeeded for one output, so a later wallet can skip the transactions behind it.

The proof is bound to an **evidence root**: SHA-256 over the txids of every transaction in that walk, including the deploy and the transaction that wrote the output. Each txid is its 32 bytes in internal byte order. The txids are sorted as raw bytes, concatenated and hashed.

A proof type is registered by a revision of this document or by a companion document, which gives the proof bytes and a verification procedure. The procedure MUST accept or reject with no trusted signer. It MUST reject a proof whose evidence root, asset id, output or amount is not the one presented. A proof whose validity rests on any party's signature, the issuer's included, is not a check this document accepts, because it would make that party part of validity (BRC-251 test 2).

This document registers no proof type.

A wallet MUST ignore a proof of an unregistered type, or one its verifier rejects, and walk the transactions instead. A proof the verifier accepts MAY end the walk at that output. The new transfer, from the spent inputs forward, is still validated under BRC-255 §7. The proof covers the asset rules for the skipped history. It does not say whether the new transaction is mined.

## Security considerations

- A sender can omit a transaction the recipient still needs. The recipient fetches it, or the output stays uncredited.
- A host can refuse a txid. It cannot substitute a transaction, because the hash would fail.
- The sender's record is a guess from delivery, not knowledge of the recipient's frontier. A delivery to one recipient says nothing about another, nor about a recipient that refused the transfer or reinstalled and lost its records. That wallet fetches what it does not hold.
- A proof that checks for one evidence root fails for another. Until a type is registered, no proof skips a walk.
- Spending an older branch changes the size of a package, not the result of the walk.
- An output whose transaction is not yet mined is still unconfirmed, as BRC-255 §7 says.

## Implementations

- **HandCash Desktop and Mobile** implemented §1 to §3 for the earlier token encoding from version 1.3.555: they record validations, fetch a missing ancestor by txid, omit ancestors behind a recipient's accepted deliveries, and spend the inputs whose remaining walk is shortest. They ignore compressed proofs, as this document registers none. The BRC-255 port is in progress.
