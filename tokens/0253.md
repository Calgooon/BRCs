# BRC-253: Countersigned Tokens

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

A countersigned token is a [BRC-162](./0162.md) fungible token whose issuer must accept every transfer before it exists. Every token output has a locking script that needs two signatures: the holder's and the issuer's. The issuer's signature is the acceptance. A transfer the issuer refused cannot be valid Bitcoin, so it can never be broadcast, mined or credited.

The sender asks the issuer for acceptance peer to peer. The request goes to the issuer's identity key over a [BRC-246](../peer-to-peer/0246.md) data channel, or through a [BRC-33](../peer-to-peer/0033.md) message box when no channel is open. The issuer publishes no endpoint. The recipient checks a transfer offline from one [BRC-30](../transactions/0030.md) Extended Format transaction. It walks no lineage and needs no overlay. Once those checks pass, the transfer is final against the sender.

## Motivation

An issuer of a regulated asset, such as a stablecoin, must be able to refuse a transfer: from a frozen holder, to an unregistered recipient, or over a limit. Today that is done by an overlay that admits each transfer ([BRC-207](../wallet/0207.md)), with attestations so that a payee can accept offline ([BRC-175](../payments/0175.md)). That design has two costs:

- **Latency.** A wallet needs a current overlay answer before it spends or accepts. Accepting before that answer needs attestations, a walk to attested outputs, and settlement later.
- **Unclear outcomes.** A payment can be credited and later reversed when settlement fails, or held without being credited. An attestation shows the output was admitted, not that it is still unspent. A payer's inputs stay reserved after a decline. Trust modes, complete-set rules and eviction all decide what a balance means.

Both costs come from the same place. Acceptance is a statement about a transaction, made outside it, so a transaction can exist without the statement, and parties must reason about the gap.

This document closes the gap. The issuer's acceptance is a signature inside the transaction, and the locking script makes it necessary. There are three outcomes and each is final: the issuer signed, the issuer refused, or the request was cancelled.

## Terms

- **Issuer key set.** `m` and `n` with `1 ≤ m ≤ n ≤ 5`, and `n` compressed secp256k1 public keys, fixed at deploy. Any `m` of them accept a transfer. More than one key lets the issuer run several services, so one being offline does not stop transfers.
- **Countersign clause.** The locking script below, written after the BRC-162 prefix.
- **Countersigned output.** An output with the token's id in its BRC-162 prefix, and the countersign clause naming the deploy's issuer key set.
- **Resolved.** A received output that passed the checks in [§10](#10-resolution). A resolved output counts in the balance and may be spent.

## Specification

### 1. Deploy

The deploy is a BRC-162 deploy at output 0, with fixed supply or authority. Every token output it creates, value or authority, is a countersigned output, and the issuer is its first holder. The token id is the deploy outpoint.

Its payload MUST be a DAG-CBOR map containing `req` with exactly the entry `{"countersign": 1}`. It MAY contain BRC-162's `sym`, `dec` and `icon`, and `hdl`, the issuer's [BRC-169](../peer-to-peer/0169.md) handle as text. The payload MUST NOT contain a URL. The issuer is reached by identity key, never by an address in the token.

The issuer key set is read from the deploy output's clause. A wallet obtains the deploy body once per token from any source, and keeps it only when the body hashes to the token id's txid.

### 2. Countersign clause

```
OP_DUP OP_HASH160 <holder pubkey hash, 20 bytes> OP_EQUALVERIFY OP_CHECKSIGVERIFY
OP_m <issuer key 1> … <issuer key n> OP_n OP_CHECKMULTISIG
```

`OP_m` and `OP_n` are `OP_1` to `OP_5`. Keys are 33-byte compressed, in the order the deploy lists them. The full locking script is:

```
<token id> <amount> OP_2DROP [<payload> OP_DROP] <countersign clause>
```

The unlocking script is:

```
OP_0 <issuer signature 1> … <issuer signature m> <holder signature> <holder pubkey>
```

Issuer signatures are in the order of their keys. The holder's signature MUST use sighash `ALL | ANYONECANPAY | FORKID` (`0xC1`). Every issuer signature MUST use `ALL | FORKID` (`0x41`).

The holder signs only its own input and every output, so the issuer can add its fee input without changing what the holder approved. The issuer then signs everything, so no input or output can change after acceptance.

### 3. Closure

Every token output of a countersigned token MUST be a countersigned output with the deploy's issuer key set. The issuer MUST NOT countersign a transaction that writes the token's id to any other script. A wallet MUST treat an output of the token without the clause, or with a different key set, as not a holding of the token.

Since every spend needs the issuer and the issuer countersigns only transactions that keep the clause, every holding traces through issuer-accepted transactions back to the deploy. Nobody has to walk that history.

### 4. Building a transfer

A sender builds one transaction:

1. Inputs are resolved countersigned outputs of one token. It has no other inputs. The issuer adds the only other one.
2. Outputs are countersigned outputs: one per recipient, locked to the recipient identity key's pubkey hash, and change when needed. If the issuer's current terms (§8) ask for a fee in tokens, it adds that output too. Amounts sum exactly to the inputs.
3. Each output carries 1 satoshi. The sender does not fund the transaction.
4. The user approves the token, the amount and each recipient. A satoshi payment grant, an auto-pay limit or a generic basket grant MUST NOT approve it.
5. The holder signs every input (sighash `0xC1`). Each unlocking script holds only `<holder signature> <holder pubkey>`.

The sender serializes this transaction in Extended Format. Its **request id** is the lowercase hex SHA-256 of those bytes.

### 5. Requesting acceptance

The sender seals a request to the issuer per BRC-78:

```json
{
  "v": 1,
  "t": "request",
  "token": "<token id, txid_vout>",
  "ef": "<Extended Format transaction, base64>",
  "recipients": [{ "vout": 0, "identityKey": "<66 hex>" }]
}
```

`recipients` names the identity key behind each recipient output, so the issuer can apply its rules about who may hold the token. It MAY also list the change output.

The sender sends it on an open BRC-246 data channel to any device of an issuer key. Otherwise it sends it through BRC-33 `sendMessage` to that key's message box, in box `countersign`. It finds that box by the issuer's handle `hdl` per BRC-169, or by a box it already knows for that key. A sender MAY send the same request to several issuer keys, because the issuer accepts a request at most once (§6).

While a request is outstanding, the sender MUST NOT spend its inputs in a different transaction. It MAY send the same request again. Repeating a request is safe.

### 6. Issuer processing

The issuer keeps the set of countersigned outputs it has accepted and not seen spent. For a request it:

1. checks that every input is in that set and is not reserved by another request;
2. checks every holder signature, the clause and key set of every output, and that amounts sum exactly;
3. checks that each recipient output pays the named identity key's pubkey hash, and applies its own policy: frozen holders, registered recipients, sanctions, limits;
4. checks its fee terms;
5. in one durable step: marks the inputs spent by this request, adds one input of its own whose value covers the network fee and any carrier-satoshi deficit, signs every token input and its own input, and records the signed transaction under the request id;
6. replies, delivers (§9) and broadcasts the transaction. Replying does not wait for broadcast.

**Accept once.** The issuer MUST NOT countersign two transactions spending the same output. A repeated request returns the transaction already recorded. The fee input adds no change output, because the holder already signed the outputs. The issuer keeps inputs of a few fixed sizes for this.

Because the only non-token input belongs to the issuer, the sender has nothing left to double spend once the issuer accepts.

### 7. Decisions

A reply is sealed to the sender per BRC-78 and returned on the channel or in the sender's box `countersign`.

```json
{ "v": 1, "t": "accepted", "token": "…", "request": "<request id>", "ef": "<signed Extended Format transaction, base64>" }
{ "v": 1, "t": "refused",  "token": "…", "request": "<request id>", "reason": "<code>", "terms": { "…": "§8, when reason is fee" }, "signature": "…" }
{ "v": 1, "t": "cancelled", "token": "…", "request": "<request id>", "signature": "…" }
```

`accepted` needs no further signature. The transaction is the proof.

`refused` and `cancelled` are signed by an issuer key with the BRC-42 child for protocol `[2, "countersign decision"]`, key ID `1`, counterparty `anyone`. The signature is DER-encoded ECDSA, with low-S and RFC 6979 nonces, over SHA-256 of the UTF-8 preimage `countersign\nv1\n{t}\n{token}\n{request}\n{reason}`, where `reason` is empty for `cancelled`.

Reason codes: `unknown_input`, `spent`, `invalid`, `frozen`, `recipient`, `limit`, `fee`, `policy`. Wallets SHOULD show the reason to the user.

After `refused` or `cancelled`, the inputs are the sender's to use again. The issuer never accepts that request id.

**Cancel.** A sender with an outstanding request MAY send `{ "v": 1, "t": "cancel", "token": "…", "request": "…" }`. The issuer answers with `accepted` if it already accepted, or with `cancelled`. Either answer ends the request.

A sender with no answer waits. It loses nothing, because without an answer no transaction exists.

### 8. Terms

An issuer that charges a fee in tokens publishes signed terms, with the same signature construction as §7, over `countersign\nv1\nterms\n{token}\n{fee}\n{feeScript}\n{validUntil}`:

```json
{ "v": 1, "t": "terms", "token": "…", "fee": "<units, decimal string>", "feeScript": "<countersigned locking script, hex>", "validUntil": 0, "signature": "…" }
```

`validUntil` is in Unix seconds. A sender caches the terms and applies them until they expire. A `fee` refusal carries the current terms, so a retry succeeds. An issuer that charges nothing publishes none, and a request needs no fee output.

### 9. Delivery

The issuer SHOULD deliver the accepted transaction to each recipient. The sender SHOULD deliver it too. Each delivery is sealed to the recipient per BRC-78 and sent on a BRC-246 channel or through BRC-33 to the recipient's box `inbox`:

```json
{ "v": 1, "t": "transfer", "token": "…", "ef": "<signed Extended Format transaction, base64>" }
```

A repeat of a transfer already received is the same transfer. Issuer delivery saves the sender's leg: the recipient can hold the transfer before the sender has read the issuer's reply.

### 10. Resolution

A recipient resolves a transfer offline:

1. It holds the deploy body for `token` and reads the issuer key set from it.
2. It parses the Extended Format transaction. For every input whose claimed spent script carries the token's id, that script MUST be a countersigned output with the deploy's key set, and the input MUST pass script validation against the claimed script and satoshis.
3. Every output carrying the token's id MUST be a countersigned output with that key set. Amounts MUST satisfy BRC-162's transition rules, read from the claimed spent scripts: a transfer sums exactly, and only a spend of the token's authority may mint.
4. It finds the outputs locked to its own identity key's pubkey hash.

Each issuer signature commits to the spent output's script and satoshis, so a false claim about either fails step 2. The issuer signs only outputs it has accepted, so step 2 also shows the inputs are genuine. The recipient needs no parent bodies, no lineage and no overlay answer.

The recipient MUST NOT credit an output that fails a step. It records the outputs that pass, then acknowledges the message. A resolved output is final against the sender. The transaction needs no confirmation and no settlement step. A wallet SHOULD still broadcast the transaction it received. Broadcasting is idempotent.

### 11. Filing

A wallet files countersigned outputs under basket `countersigned`, with tag `countersigned:<tokenId>`. When present, `customInstructions` MUST be a UTF-8 JSON object serialized as a string, with `id`, `amt`, `sym` and `dec` when known. The script is authoritative: a balance is the sum of resolved outputs' script amounts per token id.

## Security considerations

- **Trust.** Holders trust the issuer to accept each output once and to stay available. That is the trust a regulated asset already asks for. The issuer cannot move a holder's tokens, because every spend also needs the holder's signature.
- **Double acceptance is provable.** Two valid transactions spending one countersigned output, both carrying issuer signatures, prove that the issuer broke the accept-once rule. Anyone holding both can show it.
- **Availability.** Transfers wait while no issuer key answers. Nothing is credited or lost while a request waits. Extra keys help only as far as accept-once allows: services that can each accept alone MUST share one consistent record of accepted outputs, or two of them could accept different spends of one output. Availability is therefore bounded by that record.
- **Issuer exit.** If the issuer stops for good, every output is frozen for good. No path lets a holder move, redeem or burn without the issuer.
- **Composability.** Closure fixes the script, so a holder cannot put the token in another contract, a marketplace covenant or a multisig without the issuer countersigning that use.
- **Fees and spam.** The issuer pays every network fee. Without fee terms or rate limits, small transfers cost the issuer money.
- **Key compromise.** A stolen issuer key can accept transfers that break the issuer's policy, or accept an output twice. It cannot spend without the holder. With `m ≥ 2`, one stolen key is not enough. This draft has no key rotation (see Open questions).
- **Freeze, not seizure.** The issuer freezes by refusing. It cannot move a frozen output. It can mint replacement supply when its authority permits, leaving the frozen output unspendable for good.
- **Replay.** Accept-once is per output. A request id identifies the exact transaction the holder signed, so a repeated request is the same request.
- **Holder signature scope.** `ANYONECANPAY` lets anyone add inputs to a holder's signed transaction. The outputs stay fixed, and no spend is valid without the issuer, who adds only its own fee input.
- **Privacy.** The issuer sees every transfer and the identity key behind each recipient. Outputs reuse the recipient's identity address, which links that recipient's receipts on chain. Both are deliberate for a regulated asset and unsuitable for others.
- **Reorganization.** A reorganization can drop a transfer from the chain. The issuer still holds and rebroadcasts the transaction it accepted, and cannot accept another spend of those inputs.

## Rationale

**Why the acceptance is in the script.** If acceptance were a separate signed statement, a transaction could reach the chain without it, and every later holder would need the statement for every hop. With the clause, a transaction without acceptance is invalid, and the recipient checks one transaction.

**Why Extended Format, not BEEF.** The issuer's signature commits to the script and amount it spends. So a recipient that is given those two things can check them. Nothing older than the transfer is needed. A one-input, two-output transfer with a 1-of-2 key set is about 700 bytes.

**Why the issuer funds the transaction.** If the sender supplied a satoshi input, it could double spend that input and void an accepted transfer, leaving the token inputs stuck behind the accept-once rule. With the issuer's input as the only other input, acceptance is final the moment it is signed.

**Why no offline payment.** Acceptance before resolution means the issuer must be reachable when a transfer is made. A live channel makes that one round trip, typically under a second. An asset that must move with no network belongs under [BRC-175](../payments/0175.md), which accepts counterparty risk to do it.

**Compared with an overlay.** An overlay applies issuer policy by admitting transactions after they are built, and then has to say what an unadmitted output means. Here a policy refusal leaves nothing behind, and there is no admitted-but-maybe-spent state to attest.

## Open questions

1. **Key rotation.** The key set is fixed in every output. Rotation today means a migration the issuer countersigns to a new token. A rotation statement signed by the old key set may be better.
2. **Swaps.** A token-for-satoshi swap brings in the counterparty's satoshi input, which could be double spent. One option is that the issuer accepts swaps only when that input is mined.
3. **Pre-accepted spends.** The issuer could sign `SINGLE | ANYONECANPAY` for one input and its paired output ahead of time, giving a voucher a holder can spend once to a fixed recipient while the issuer is away.
4. **Derived holder keys.** Holding under a [BRC-42](../key-derivation/0042.md) key with a [BRC-69](../key-derivation/0069.md) linkage disclosed to the issuer would stop identity-address reuse.

## Test script

[`media/0253/countersign.mjs`](./media/0253/countersign.mjs) builds a 1-of-2 transfer with `@bsv/sdk`'s interpreter. The holder signs, then the issuer adds its fee input and countersigns. The script checks that the input verifies from the Extended Format transaction alone. It also checks that each of these fails: a false spent amount, script or satoshi value; a holder signature without the issuer; a countersignature by a key outside the set; and any change to outputs or inputs after the issuer signs. Run `npm install && npm test` in that directory.
