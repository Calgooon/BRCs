# BRC-234: Progressive Contraction of Chain-Scanned Address and Transaction Index Spaces

Ty Everett (ty@projectbabbage.com)

> **Status:** Proposed specification. The schedule and service contract below are normative for voluntary conformance. Publication does not assert an implementation, provider commitment, or deployed multicast transport.

## Abstract

This BRC proposes a voluntary retirement profile for general-purpose, publicly queried BSV mainnet address and transaction-ID indexes. Block `1,000,000` anchors a schedule with finer early contractions and progressively longer scheduled intervals. Advancement requires both a calendar threshold and cumulative non-coinbase transaction volume. The final calendar threshold is 78 months after the anchor; low volume can postpone it indefinitely.

TXID eligibility gates both index families. A transaction is eligible for TXID lookup when its displayed TXID passes the active TXID filter, regardless of the addresses it contains. A generalized address-history record additionally requires its P2PKH address to pass the active address filter. Grandfathered covered-balance metadata is the explicit exception defined in section 6. At the final accepted-chain stage, the fixed filters retain the namespaces beginning with `1ChickenNugget` and thirteen hexadecimal `9` digits; they do not require complete service shutdown.

Stages and balance state are derived exclusively from the currently accepted mainnet chain. Reorganizations roll back orphaned stage triggers and disqualification events. Data removed from active use must remain recoverable under a mandatory hold of at least 100 accepted-chain blocks before destructive removal. Previously purged records must be reconstructed if deeper reorganizations broaden coverage; a service must report unavailable rather than misrepresent missing data.

A balance response covers only qualifying funds and MUST be labeled accordingly. Services providing it must also observe spends outside the TXID-filtered stream. A disqualifying spend ends the address's balance guarantee while that event remains in the accepted history, as defined in section 6.

The profile changes participating lookup services. It does not change consensus, script validity, address validity, or custody. Independent providers remain free to operate other products.

## Motivation

Address-based discovery requires an intermediary to find transactions relevant to a wallet. A universal TXID retrieval service has a different function: it returns transaction data when the caller already knows the identifier. Both create dependencies on comprehensive third-party indexes. This proposal progressively removes those dependencies from participating services and reduces the lookup records they retain. Transacting parties and their chosen storage providers should preserve and exchange the data needed for their own transactions, rather than assume that a universal fallback will remain available.

The tandem TXID requirement also supports future selective transaction propagation. [BRC-80](./0080.md) describes version- and TXID-based multicast subscriptions; [BRC-83](../transactions/0083.md) discusses distributed transaction processing and aggregation. With a complete TXID-sharded feed, an indexer could receive the permitted transaction subset and use it for both TXID lookup and eligible address records. An address-only filter would still require examining transactions across all TXIDs to discover qualifying outputs.

That propagation benefit is conditional on the transport and its coverage. BRC-80's illustrated mapping carries 48 TXID bits, while this profile eventually tests 52. That mapping would require receiving the broader 48-bit shard and filtering the last four bits locally, or a transport extension. Its version field also precedes the TXID field: covering all transaction versions must be addressed explicitly by an eventual subscription profile. This BRC does not deploy multicast or specify that binding. Complete spend observation, late-join recovery, and missing-data detection remain separate requirements for balance guarantees.

[BRC-49](./0049.md) motivates moving away from user-facing addresses. [BRC-29](../payments/0029.md), [BRC-42](../key-derivation/0042.md), [BRC-62](../transactions/0062.md), [BRC-95](../transactions/0095.md), and [BRC-100](../wallet/0100.md) provide a direction for direct transaction delivery and associated remittance data. [BRC-125](../payments/0125.md) initiates BRC-29 payments. BRC-29 still uses P2PKH outputs: this proposal retires a discovery dependency, not the P2PKH script template.

The surviving namespace intentionally permits optional grinding for constrained legacy use. Finer initial steps soften the initial difficulty cliff; longer later intervals provide more preparation time as difficulty rises. These policy choices do not establish that later grinding is affordable or that retained index size has a fixed upper bound.

## Specification

The terms **MUST**, **MUST NOT**, **SHOULD**, and **MAY** apply to services voluntarily claiming conformance.

### 1. Scope and anchor

The activation block is BSV mainnet block `H0 = 1,000,000`. For a block at height `H`, `MTP(H)` is the median of the timestamps of that block and its ten immediate ancestors, expressed as Unix seconds. The anchor `T0 = MTP(H0)` is interpreted in UTC. A publication date is not an activation date, and no exact future calendar date is asserted before the anchor is known.

A service MUST declare whether it offers address lookup, TXID lookup, or both. Generalized address-history lookup always applies both current filters, including when the service does not expose a TXID endpoint. Covered-balance and covered-outpoint responses have the narrowly defined grandfathering exception in section 6. TXID lookup never requires any contained address to pass the address filter. There is no separate optional combined-filter family.

Address coverage is restricted to canonical, case-sensitive, checksum-valid mainnet Base58Check P2PKH addresses with version byte `0x00`. TXID comparisons operate on the conventional 64-character, big-endian hexadecimal display string, normalized to lowercase. Implementations MUST NOT apply the leading-bit test to the start of a little-endian internal hash buffer.

For this profile, a P2PKH output is the exact 25-byte locking script `76a914{20-byte HASH160}88ac`; other script forms are outside the address family. Canonical mainnet address encoding is Base58Check of `0x00 || HASH160`, using the first four bytes of double-SHA256 of those 21 bytes as checksum. Decoding MUST validate length, checksum, version, and canonical re-encoding. ASCII case MUST NOT be folded or surrounding whitespace silently removed.

For an already validated 64-hex-character TXID, the exact bit predicate is:

```text
txidMatches(displayTxid, requiredBits):
  t = lowercase(displayTxid)
  whole = requiredBits // 4
  partial = requiredBits % 4
  if t[0:whole] != "9" repeated whole times: return false
  if partial == 0: return true
  return (hexValue(t[whole]) >> (4 - partial)) == (9 >> (4 - partial))
```

Consensus validation, underlying block archives, private wallet records, proof processing, and purpose-built overlays are outside this general-purpose index profile. Indexes MAY expose mempool information, but any such coverage MUST be identified separately from confirmed history and covered balances.

### 2. Stage filters and volume gates

The normative schedule has 27 contractions: stages 1 through 17 refine the first three characters after the address's mandatory leading `1`, ending at `1Chi`, while refining the first twelve TXID bits toward `999`. Stages 18 through 27 then add whole characters. Stage 0 allows all mainnet P2PKH addresses and all TXIDs.

In the table, brackets contain an explicit set of permitted characters at one position. They are not a literal part of an address. The string before the brackets must match exactly; the remainder of the address is unconstrained. An unbracketed entry is an ordinary textual prefix.

The TXID column gives the number of leading bits that must equal the same number of leading bits of `9999999999999`, using the display string's most-significant bit first. Thus one bit admits initial hex digits `8` through `f`; two bits admit `8` through `b`; three admit `8` or `9`; four require `9`. Extra digits remain unconstrained. This preserves the exact final thirteen-`9` prefix while allowing finer initial steps.

All volume thresholds count non-coinbase transactions after `H0`, not transactions retained by either index. Intermediate thresholds linearly subdivide the original full-character volume milestones; these subdivisions are fixed policy gates, not a measured adoption or migration-readiness metric.

Later whole-character steps remain larger: one more TXID hex digit gives a 16-fold uniform-hash work factor, while address-character probabilities depend on Base58Check encoding.

### 3. Calendar and scale schedule

Let `V(H)` count non-coinbase transactions in accepted mainnet blocks `H0 + 1` through `H`, inclusive; `V(H0) = 0`. Counts and arithmetic MUST support values beyond 32-bit unsigned range without overflow.

The calendar gates are defined as follows: the initial migration runway ends at `G = T0 plus 6 calendar months`. The final earliest date is `E = T0 plus 78 calendar months`. Calendar-month addition preserves UTC time of day and clamps the day to the last day of the target month where necessary. Both additions are performed directly from `T0`.

Stage 1 has earliest date `T(1) = G`. For the 26 intervals between stages 1 and 27, define integer weights:

```text
w(i) = 11^(i - 1) * 10^(26 - i), for i = 1..26
W    = sum(w(i), i = 1..26)
D    = E - G, in integer seconds
T(s) = G + ceil(D * sum(w(i), i = 1..s-1) / W), for s = 2..27
```

Thus scheduled intervals after the first contraction grow geometrically by approximately 10%, with only whole-second rounding. The six-month runway is a separate grace period, not the first interval in that geometric series. The last calendar eligibility gate is exactly `E`; activation additionally requires sufficient volume and the following accepted block. This normalization fits increasing intervals inside the retained 78-month earliest horizon; it does not assert that chain growth follows a measured 10% curve.

At accepted block `H`, a stage is eligible only when both `MTP(H) >= T(s)` and `V(H)` reaches its table threshold. The candidate stage is the highest eligible stage, or 0 when none qualifies. A newly reached candidate applies from the accepted child of the triggering block, not to the triggering block itself. Before `H0` is available there is no activated profile and no advancement calculation.

No stage has a guaranteed activation date. Calendar gates are lower bounds; volume gates may defer every contraction indefinitely. Direct jumps are permitted: if volume catches up after several earliest dates have passed, the candidate can advance several stages in one block. Longer scheduled intervals are not guaranteed dwell times between actual contractions.

For illustration only, with `T0 = 2028-10-20 00:00:00 UTC` and all volume gates met, the calendar gate for stage 1 opens after six months, stage 5's gate for `1C` opens after about nine months, stage 11's gate for `1Ch` after about 16.5 months, stage 17's gate for `1Chi` after about 29.7 months, and stage 27's final-prefix gate exactly 78 calendar months after the anchor. Each activation occurs in the accepted child of its qualifying trigger block. This is not a forecast for block `H0`.

### 4. Accepted-chain activation, reorganization, and notice

The current accepted mainnet chain is the sole authority for the anchor, cumulative volume, stages, funding admissions, UTXO state, and address disqualification. A rejected side branch MUST NOT change those results. State previously derived from an accepted branch MUST be undone when that branch is orphaned. There is no service-local highest-ever stage or irreversible disqualification independent of the accepted chain.

Let `candidate(B)` be the highest stage whose calendar and volume gates are met at accepted block `B`, using the anchor on that same chain. Before the anchor, candidate and event stage are 0 and the profile is not yet activated. For each accepted block:

```text
eventStage(B) = candidate(B.parent)   // 0 when the parent precedes H0
activeStage  = eventStage(acceptedTip)
pendingStage = candidate(acceptedTip)
```

The pending stage is a future change only when it exceeds the active stage. It is not another activated stage. This preserves following-block activation: a trigger block uses its parent's candidate, and its accepted child uses the candidate it establishes. Within one accepted chain, calendar and cumulative volume gates do not move backwards. Direct jumps remain permitted. A reorganization can change the anchor, remove a gate crossing, and lower either the active or pending stage.

A service MUST process funding and spends in accepted-chain order using each block's own event stage. A late-joining service and an existing service at the same accepted tip MUST derive the same stages from the same chain data, regardless of previously observed forks or their startup times. Caches and checkpoints MUST be bound to block hashes and validated ancestry, not heights alone. A service MUST NOT backdate its current stage to historical transactions or substitute a discarded branch's activation history.

On a reorganization, the service MUST find a verified common ancestor, roll back orphaned effects, and replay the accepted replacement branch. It MUST recompute affected gates, funding admission, grandfathering, covered-outpoint spends, and address disqualification. If `H0` changes, its hash, MTP anchor, calendar gates, and all dependent state MUST be recomputed. If the accepted chain no longer contains `H0`, the profile is inactive; no previously observed anchor or stage may remain authoritative. Orphaned evidence MAY remain in audit logs but MUST NOT govern current query results or balance refusals.

Before publishing a chain view, services MUST durably checkpoint its anchor, accepted tip, stage, pending stage, relevant trigger/effective block identities, indexed-through watermark, balance state, and watch continuity as a coherent state. A restore MUST verify that its checkpoint is on the accepted chain, undo any rejected state, and complete required replay/backfill before making coverage claims. Unknown or inconsistent state is unavailable, never zero or a genuine lookup miss.

#### 4.1. Mandatory 100-block recovery hold

Query withdrawal and destructive data removal are separate operations. When a profile transition makes previously required data unnecessary for the active view, the service MUST retain enough durable data to undo that transition and reconstruct its affected state for at least **100 accepted-chain descendants**. This minimum uses the same block count as the coinbase maturity rule; it does not make 100 blocks a finality rule or change coinbase spendability.

Let `R` be the accepted block at whose processing the data first becomes unnecessary, and let `H` be its height. For a stage contraction this is the effective activation block, not its preceding trigger block. For a spend or disqualification it is the event block. A late-adopting service withdrawing existing coverage anchors its hold at its accepted entry snapshot; it MUST NOT backdate that hold to a stage change before its own withdrawal. Each retirement batch MUST be bound to `R`'s hash and height. A record with multiple dependencies remains protected until every applicable dependency and hold has ended.

The earliest possible purge height is `H + 100`, and purge is permitted only after that block has been accepted with `R` as its ancestor. A configured longer minimum replaces 100 in that height calculation. At `H + 99` purge is forbidden; at `H + 100` it is permitted only if no longer retention, active-state, or recovery obligation still requires the data. These are 100 descendants, not 100 confirmations counting `R` itself. Orphaned blocks and rejected side branches contribute no age. Wall-clock time, another branch's numeric height, restart, or a cached highest-seen height cannot satisfy the hold.

During a reorganization, retirement workers MUST pause until the accepted ancestry and recovery requirements are verified. If `R` is orphaned, its purge authorization is void: undo the transition and restore required state. If the data is still unnecessary under the replacement history, establish its retirement anchor from the corresponding verified accepted-chain event. If the former event cannot be established there, use the accepted recovery snapshot as a new anchor. A lower accepted tip can make an unexpired hold longer; it cannot be ignored because the data previously approached its purge height.

The hold covers excluded transaction and address-history records, previous covered-outpoint/admission/spend state, disqualification undo state, and the checkpoints or per-block undo/replay material needed to restore the affected view. A compressed or different recovery representation MAY replace an active index entry, but MUST preserve the information needed for verified restoration. The recovery copy MUST remain durably under the service's control and available to its recovery procedure; an unverified expectation that a third party might later supply it is insufficient for this hold. This rule does not require admitting or storing every newly observed nonqualifying transaction body.

Protected data MAY be moved out of the queryable index immediately into recovery-only storage; it MUST NOT be served in violation of the active filters. Services MAY retain it for longer than 100 descendants. They MUST retain it longer whenever needed by the active profile, an ongoing rollback/replay/backfill, or another unexpired dependency. In particular, an unspent grandfathered covered output cannot expire merely because its funding or retirement block has aged 100 blocks. Destructive removal includes deleting the only usable copy or its decryption keys; replacing data with an equivalent verified durable representation is not removal.

After the hold expires, deletion MUST still remain logically recoverable for deeper reorganizations. Operators MUST have a verified reconstruction path, such as retained block archives or a complete independent retrieval source, for data that can become covered again. The 100-block hold supplies a minimum recovery window, not permission to retain a rejected chain's state or abandon accepted-chain correctness after a deeper reorganization. Deleting index records is not permission to lose the only recovery path for required accepted-chain data.

If a lower stage broadens coverage, services MUST rebuild all newly eligible historical records, including records predating the fork or `H0`, not merely process new replacement blocks. An address that regains coverage after losing a prefix or disqualification also requires verified admission and spend history through the declared snapshot. Until that reconstruction and watch backfill are complete, affected operations MUST return `unavailable` and the service MUST expose `rebuild_pending`. Verified individual hits may be returned with explicit incomplete-coverage status, but missing records MUST NOT be presented as complete misses and no unsupported accurate balance may be returned. No particular rebuild duration or availability SLA is promised by this profile.

An existing service MUST give clients at least **14 calendar days' public notice before its first withdrawal of previously offered coverage under this profile**. Notice MUST explain tandem filtering, the schedule, volume uncertainty, possible direct jumps, accepted-chain rollback and rebuild behavior, the 100-block recovery hold and deeper-reorganization limits, covered-balance limits, and migration options. The service MUST continuously publish current rules, pending changes, and coverage readiness. A late adopter gives notice before entry and derives its entry stage from accepted-chain history; the notice period does not reset the chain schedule. A provider's independent business closure is not a more advanced BRC stage.

### 5. Admission, retirement, and lookup responses

Using the predicates defined by the active-stage table:

```text
requiredTxidBits(stage) = the stage's "Required TXID bits" table value

transactionEligible(tx, stage) = txidMatches(tx.txid, requiredTxidBits(stage))

addressHistoryRecordEligible(address, tx, outputIndex, stage) =
  outputPaysToP2PKHAddress(tx.outputs[outputIndex], address)
  AND addressMatches(address, stage)
  AND txidMatches(tx.txid, requiredTxidBits(stage))
```

An address-history service MUST apply both current conditions. It MUST NOT include a transaction failing the TXID filter merely because one of its outputs pays a qualifying address. A TXID service MUST NOT exclude an otherwise qualifying transaction because its addresses fail the address filter or have lost balance coverage. Successful raw-transaction retrieval returns the complete transaction; address filtering is not transaction redaction.

At each activation, services MUST immediately stop admitting excluded generalized transaction/address-history records and stop serving excluded generalized lookups. They MUST retire those excluded records from the active contracting index, including records predating `H0`, while obeying section 4.1's recovery hold before destructive removal. Covered-balance metadata still required under section 6 is exempt from retirement. Recovery-only retention required by section 4.1 is conforming; it is not completed storage reclamation. Retaining a complete active index and merely hiding it behind a filtered API does not satisfy retirement. An implementation may reclaim storage asynchronously after its holds expire, but MUST expose the actual pending/protected state and MUST NOT claim reclamation before it occurs.

Minimal stage history, spend-observation continuity, covered-balance state (including grandfathered outpoints and their admission metadata), and accepted-chain disqualification metadata MAY be retained to enforce this BRC. This is an explicit exception for operational state, not permission to preserve a hidden general-purpose transaction or address-history index. Original blocks, proofs, private records, and separately declared products may be retained independently.

Core TXID coverage includes every accepted-chain transaction from genesis through the declared indexed-through block whose TXID passes the active filter. It includes coinbase transactions; coinbases are excluded only from the schedule's volume counter. Core address history covers matching P2PKH output records over that same complete range, subject to the retirement exception for addresses disqualified by accepted-chain history. Here address history means funding/output discovery, not an unconditional complete history of all address activity.

A service MUST NOT silently use a shorter history window, omit qualifying transactions, or map missing ingestion/backfill data to a core-profile miss. Incomplete history requires an unavailable/partial-service declaration until restored. A hit still needs a transaction whose computed TXID matches the returned identifier and whose claimed confirmation is in the accepted chain. A miss is only an absence from the complete declared chain snapshot, not proof about later blocks or another chain. A service offering historical windows instead of this core completeness contract MUST identify that product separately and MUST NOT claim complete core-profile coverage.

Lookup responses MUST distinguish an in-scope hit, an in-scope miss, and outside-coverage refusal. Invalid requests MUST be distinguished from a valid key outside coverage. Address history is filtered history: a miss means no matching indexed record within the declared coverage, not that the address has received no payments. Disqualified-balance and temporarily unavailable responses defined below MUST NOT be translated into zero balances or claims of nonexistence.

Machine-readable status MUST identify the index families, activation height and anchor, actual active stage, candidate stage, address rule, required TXID bits, triggering block hash and height, current accepted tip hash and height, indexed-through hash and height, pending stage and trigger, effective activation height, feature support, and retirement completion state. Partial-bit filters MUST NOT be advertised merely as a whole-character prefix.

### 6. Covered balances and accepted-chain disqualification

A **covered balance** is the sum of currently unspent outputs admitted when their funding transactions and P2PKH addresses passed the stage applicable to their funding block, subject to the address still passing the current address rule and not being disqualified by the accepted history. The service MUST label this as a covered balance, not a total on-chain address balance. A funding transaction that fails the filter applicable to its funding block does not add covered funds and does not, by itself, disqualify an address. Such ignored payments remain outside this balance promise. For pre-activation history, admission uses the unrestricted stage-0 TXID rule; later reconstruction must establish the historical admission and spend state rather than silently assume coverage. Historical admission is evaluated against the funding block's applicable stage, not the stage when a service happens to learn of or reconstruct that output. This permits verified balance initialization while still forbidding generalized lookup admission under an obsolete filter.

An admitted unspent output is **grandfathered** when its funding TXID ceases to pass a later filter. Tightening the TXID filter MUST NOT, by itself, remove that output from the covered balance. The service MUST preserve its outpoint, amount, required script/address information, and historical admission decision, and MUST continue watching it for spends until it is spent or the address loses coverage. This obligation is independent of retiring the funding transaction from current generalized lookup and filtered address history. A covered-outpoint response MAY identify that historical funding TXID and its admission stage as balance-state metadata; this does not make the transaction eligible for generalized TXID lookup again. A covered balance may therefore remain positive even when the current filtered history has no matching funding transaction.

The address itself is not grandfathered: if it fails the current address rule, the service MUST refuse a covered-balance guarantee and MAY stop actively indexing and watching its covered set. Previously required recovery data remains subject to section 4.1's hold. The service MUST distinguish that coverage loss from a zero balance. Reorganizations still require undoing orphaned funding and ordinary UTXO changes; grandfathering does not preserve funds absent from the accepted chain.

Every spend is evaluated against the stage applicable when it occurs. A spend that passed that stage's TXID filter MUST NOT become disqualifying merely because a later stage excludes its TXID. Services MUST preserve enough stage history and decision state to apply this rule during historical processing and restoration without retaining retired generalized lookup records.

Disqualification is triggered only by a confirmed spend in an accepted block, evaluated at the event stage derived from that block's accepted parent. A valid unconfirmed transaction MAY be reported as pending, but MUST NOT disqualify an address.

For each accepted block, the service derives `eventStage` from its accepted parent, then evaluates every transaction using that same stage. The block's own volume and MTP can establish a pending stage for its child, but cannot change the rule used for transactions in that same block. All transactions in one block use the same stage, independent of their position; ordinary UTXO dependencies are still processed in valid transaction order. A nonqualifying spend discovered during backfill uses the historical event stage for its block, not the service's latest stage at discovery.

The disqualification trigger applies only to spends of covered funds, including grandfathered outputs. A spend of an ignored deposit, or another output outside the covered set at that block's stage, does not disqualify the address, even when the spending TXID fails the filter. A transaction consuming both covered and ignored outputs triggers the rule if it spends at least one covered output and its TXID fails.

While guaranteeing a covered balance, the service MUST ensure complete observation of confirmed spends of every covered outpoint, regardless of the spending TXID. It MAY use a complete outpoint-spend notification mechanism instead of retaining every spending transaction. A feed containing only qualifying TXIDs is insufficient. The obligation is to detect all spends of covered funds across the network; it does not require watching spends of ignored deposits. The covered set used for a spend decision is the set applicable immediately before that transaction is processed, after applying its block's active stage and earlier transactions in that block.

On the first confirmed, validated spend of at least one covered output that fails the TXID filter applicable to its containing block, the service MUST disqualify that output's address from balance tracking. For a transaction spending covered outputs of multiple addresses, the rule applies separately to each affected address. An unvalidated transaction merely naming an outpoint MUST NOT trigger disqualification. The decision MUST identify the spending TXID, covered input outpoint, confirmation block hash and height, and event stage. It persists across restart and subsequent contractions only while supported by accepted-chain history.

If the triggering confirmation is orphaned, that marker MUST be undone. The address remains disqualified only if replay of the accepted branch establishes at least one disqualifying spend of its covered funds. Reappearance of the same TXID in another accepted block is evaluated afresh against that block's event stage and covered-set state; its prior rejected confirmation is not authoritative. If no disqualifying event remains, the service MUST restore eligibility after reconstructing and verifying the accepted-chain balance and watch history. Until then it returns `unavailable`, not `address_disqualified` based on the rejected branch. In historical replay, membership and TXID eligibility are evaluated at the event block, not at the replay's current stage.

After disqualification the service MAY stop indexing and watching the address, and MAY retire its address records subject to section 4.1's recovery hold. It MUST return an explicit retired-coverage error or refusal for accurate-balance requests. It MUST NOT report zero, a stale figure, or another amount as a conforming accurate balance while an accepted-chain disqualifying event remains. New qualifying funds do not reset an address that is still disqualified; removal of all triggering events by a reorganization permits verified restoration. These obligations concern the service's index profile, not custody or transaction validity. Qualifying TXID lookup remains unaffected.

The following cases assume the address continues to match the active address rule:

| Event | Effect on the covered balance guarantee |
| --- | --- |
| Nonqualifying incoming payment | Ignore the deposit; retain the guarantee for covered funds. |
| A later TXID contraction excludes an admitted, unspent funding transaction | Keep its covered output and spend watch; general lookup may cease. |
| Historical spend complied with its event-stage rule but fails a later filter | No retroactive disqualification. |
| Nonqualifying spend consumes only ignored funds | No disqualification of the covered balance. |
| Nonqualifying spend of covered funds is merely unconfirmed | No disqualification; report pending status separately. |
| Confirmed nonqualifying spend consumes a covered output, including a grandfathered output | Disqualify the affected address while the triggering event remains in accepted history; refuse accurate-balance claims. |
| Spending transaction passes its event-stage TXID rule | Apply the ordinary covered-outpoint debit without disqualification. |
| Reorganization removes a disqualifying confirmation and no accepted-chain trigger remains | Undo disqualification and restore verified coverage after reconstruction; return unavailable during any gap. |
| Reorganization removes a stage trigger | Recompute the lower accepted-chain stage and rebuild newly eligible historical records. |

Covered value measures confirmed, unspent, admitted outputs; it is not a promise of immediate spendability. Coinbase maturity or another independent spending restriction MUST NOT be silently equated with the covered-balance definition. An implementation MAY report mature/spendable subsets separately with their own labels.

The balance snapshot MUST be an accepted-chain block through which both historical admission and covered-outpoint spend observation are complete. Their watermarks must lie on that same chain and reach at least the balance snapshot. A provider MAY expose an older verified snapshot while catching up, but MUST identify it as an as-of response and MUST NOT label it current unless it reaches the current accepted tip. This profile does not set an availability or maximum-lag SLA. It requires truthful snapshot and continuity claims.

A lost watch interval MUST be backfilled for all affected covered outpoints, including grandfathered ones, before accuracy claims resume. Rebuilding from only the current TXID-filtered stream is insufficient. On restoration the service MUST reconstruct accepted-chain historical admissions, stage decisions, disqualification state, and spend continuity, undoing any orphaned effects. Unknown state is unavailable, not an empty balance. An address-only-history service MAY omit balance support entirely, but MUST declare that and MUST NOT imply it has performed the additional balance watch.

A service MUST NOT claim an accurate covered balance without a verified starting state, applicable disqualification history, and uninterrupted spend observation through its declared balance watermark. A gap, unavailable history, or uncertain spend status requires an unavailable response until resolved. Balance responses MUST identify the covered amount in integer satoshis, active stage, balance-as-of block hash and height, spend-observation watermark, and active/disqualified/unavailable status. A balance guarantee is an as-of claim, not an assurance about transactions the service has not yet observed.

### 7. Migration and resource considerations

Wallets SHOULD stop depending on these contracting indexes for receipt and restoration. Current BRC-29/BRC-100 integrations construct transactions with `createAction`, exchange Atomic BEEF and remittance data, and receive them with `internalizeAction`. Operators SHOULD preserve keys, transaction data, derivation parameters, proofs, and other necessary recovery material. A contracted index MUST NOT be advertised as complete recovery for arbitrary historical addresses.

Users retaining legacy coverage must keep their addresses within the current address rule, ensure funding passes the rule at admission, and ensure spends of covered outputs pass the TXID rule applicable to the spend block. Previously admitted unspent outputs survive later TXID contractions; new deposits do not inherit that exemption. A qualifying address alone is insufficient. The loss-of-coverage rule makes migration to systems without expensive universal indexing an expected outcome, rather than preserving an unconditional fallback indefinitely.

Each additional TXID bit admits half of uniformly distributed IDs; thirteen whole `9` digits require 52 bits and admit one in `4,503,599,627,370,496` uniformly distributed TXIDs. The first address bands and later Base58 prefixes have different distributions. Implementers MUST NOT assume independent 1/58 probabilities for correctness.

Generating a private key whose derived address qualifies is distinct from constructing or copying a qualifying address string. A previously ground address can be reused, and a transaction may contain many outputs. Grinding, reuse, and targeted traffic mean qualifying record counts need not follow uniform-hash estimates. This profile does not impose a hard resource bound or guarantee that late-stage grinding remains practical.

TXID sharding may reduce transaction-body delivery where a complete suitable transport exists. It does not itself eliminate spend observation, stage-volume metadata, backfill, proof acquisition, validation, or archival costs. Implementers MUST describe their actual dependencies and MUST NOT claim that this draft deploys a selective feed or provides completeness merely by defining a filter.

### 8. Logical responses and conformance state

This is a service-profile contract, not a new HTTP, multicast, authentication, payment, or discovery protocol. Endpoint paths, transport framing, and provider availability SLAs are outside its scope. An implementation MUST document how its API maps the following logical states and required metadata; a different transport must preserve their meanings.

| Logical state | Required meaning |
| --- | --- |
| `found` | A TXID or address-history result exists within the declared filter and chain snapshot. |
| `not_found` | A valid, in-scope lookup has no result in the complete declared snapshot. It is not proof of nonexistence beyond that snapshot. |
| `outside_coverage` | The key is valid but fails the active address/TXID rule, or address-history coverage was retired. |
| `covered` | A verified covered-balance result, possibly zero, with its stage and common admission/spend snapshot. |
| `address_disqualified` | The accepted history contains a disqualifying spend of covered funds. No accurate-balance amount may accompany this state. |
| `unavailable` | Required state, continuity, backfill, or verification is missing. This is not a miss or zero balance. |
| `invalid_request` | Malformed input, invalid checksum/length, or unsupported parameter encoding. |
| `unsupported` | The operation is not offered, such as covered balances on a history-only service. |
| `coverage_changed` | A multi-part/paginated request can no longer continue under its pinned stage or accepted-chain snapshot. Restart the lookup. |

Valid Base58Check addresses of another network or script type are outside this profile's coverage; malformed encodings are invalid requests. TXID input must contain exactly 64 hexadecimal characters with no `0x` prefix or surrounding whitespace; uppercase hex is accepted and normalized. An in-scope address with no covered outputs may receive a `covered` zero only after the starting state and complete watch establish that result. For balance queries, a verified disqualification on the accepted chain takes precedence over current prefix loss. A marker whose accepted-chain status is unknown or orphaned cannot justify disqualification; return unavailable until state is verified.

Every response MUST identify the profile number and version (`234`, version `1`), operation, logical state, actual active stage, accepted-chain snapshot hash and height, and the relevant completeness/watermark metadata. Status MUST also expose the explicit address-character rule, required TXID bits, candidate and pending stages, trigger/effective heights, and distinct active-index retirement and recovery-storage reclamation states. It MUST declare `minimumRecoveryRetentionBlocks = 100`, its configured retention minimum (at least 100), and protected-batch anchor hashes/heights, earliest purge heights, and reasons for longer holds. Batch details MAY use a linked or paginated status resource. If required chain metadata is unavailable, the response MUST explicitly identify unknown fields (for example, null plus a reason) instead of inventing a stage, hash, or zero value. A known pre-activation accepted chain is reported as profile-inactive, not as an orphan-derived active stage. Known stage values are integers `0..27`; hashes/TXIDs are canonical lowercase 64-hex-character strings. Heights, cumulative volumes, amounts, and exact weights are nonnegative integers with no floating-point rounding; JSON bindings MUST use decimal strings for integer quantities that might exceed safe JSON/JavaScript integer precision. A binding MUST NOT silently convert an exact integer to a rounded number.

Pagination or resumable history MUST pin the active stage and indexed-through block hash. A reorganization, activation, or other coverage change that makes that view invalid requires `coverage_changed`; pages from different views MUST NOT be silently combined. No cursor may authorize serving a lookup excluded by the current active filter.

`retirement_pending` means excluded entries have not yet left the active generalized index. Query exclusion and new-admission rules still apply immediately. `recovery_hold` means data has left active use but remains protected under section 4.1; that required retention is conforming. `reclamation_pending` means data is no longer protected but storage has not yet been reclaimed. Reclamation is complete only after the declared removal actually occurs. These states may coexist for different batches. Accepted-chain stage and disqualification metadata are checkpointed even while generalized records are removed, and are undone/replayed when their branch is rejected. `rebuild_pending` identifies a rollback or recovery that has not yet restored newly required coverage. Providers may keep separately declared archives and private records, but MUST NOT count hiding an intact active general-purpose index as completing this profile's retirement.

## Implementations and conformance evidence

No implementation, transport deployment, provider commitment, or measured resource saving is asserted by this draft.

A reference implementation SHOULD provide a stage calculator using exact integer arithmetic; table-driven address and TXID predicates; durable activation and disqualification state; a safe retirement worker; explicit coverage responses; and covered-balance/spend-observation accounting where that feature is offered.

Conformance evidence MUST cover partial TXID bits and byte order, case-sensitive Base58 membership, uppercase hex normalization, invalid encodings, calendar clamping, integer overflow, exact gate boundaries, direct jumps, restart and restore, stage rollback after reorganization, tandem admission, nonqualifying deposits, historical-spend grandfathering, disqualifying spends, accepted-chain disqualification and restoration, observation gaps, grandfathered unspent outputs, current-address coverage loss, and the distinction between filtered history and covered balance. Conformance examples MUST distinguish unconfirmed from confirmed spends, spends of ignored deposits from spends of covered outputs, mixed-input spends, and the stage applied at a block boundary. Recovery tests MUST forbid purge at `H + 99`, permit it no earlier than `H + 100` subject to other holds, reject orphan-derived purge eligibility, protect live grandfathered state and ongoing rebuilds, and exercise recovery beyond the minimum retention window.

The [machine-readable conformance vectors](./media/0234/conformance-vectors.json) fix positive and negative prefix/bit boundaries for all stages, exact calendar gates for normal/month-end/leap-year anchors, one-second and one-transaction gate boundaries, following-block transitions, rejected/orphaned branches, grandfathering, covered-only spend triggers, reorganization restoration, and recovery-hold boundaries. Their synthetic state-machine inputs do not replace mainnet block, transaction, or proof validation. They include a stage-27 volume above `2^32` to detect truncated counters.

Reorganization recovery MUST be exercised in both directions: contraction after a new accepted gate and expansion after its removal. The exercise MUST show that old branch disqualification cannot survive as a refusal, that deleted newly eligible historical records are reconstructed, and that a watch gap produces unavailable rather than an inaccurate balance. Successful scalar stage calculation alone is insufficient evidence of index-service conformance.

Operators SHOULD first run observation mode, quantify affected clients, publish notice, and validate migration and recovery. Deletion testing must show that retiring generalized lookup records does not delete independent custody, block, proof, or private-wallet data.

## Appendix A: Complete schedule and search estimates

This appendix displays the adopted 27-stage schedule. `T0` is the chain-derived anchor, not today. Both the time and volume gate must pass; the accepted chain alone determines stages, including rollback after a reorganization. Stage 0 begins at `H0` with unrestricted TXIDs, all mainnet P2PKH addresses, and zero post-anchor volume.

`Earliest` and `Interval` are approximate nominal months: `6 + 72` times the exact post-grace cumulative weight fraction, with the first interval being the separate six-month runway. Actual eligibility gates use the exact calendar endpoints and integer-second formula in section 3. A gate-crossing block establishes a stage for its accepted child; it does not use that new rule for its own transactions. A shortfall in volume can delay activation indefinitely; catch-up can skip stages.

Every address pattern and TXID pattern is a prefix; the rest of the valid address or 64-digit TXID is unconstrained. Address ranges use the ordered Base58 alphabet `123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz`, preserving case and omitting invalid characters. TXID ranges use hexadecimal order. The explicit character sets in section 2 remain authoritative.

`Key trials` is the expected number of independent candidate private keys to find a spendable address. It uses counted valid Base58Check encodings under a uniform-HASH160 model, not a blanket 1/58 approximation. `TX trials` is the expected number of independent valid transaction candidates. Key derivation and valid-transaction generation are different operations, so these columns are not hardware-throughput measurements. A candidate transaction may require re-signing depending on what is varied.

An intentional search can first find an address and then keep it fixed while varying valid transaction candidates. For that strategy, do not multiply the two columns. Address reuse amortizes key-search work across payments, while TXID work recurs per transaction and may be amortized across that transaction's outputs. An undirected stream that chooses new independent addresses and TXIDs has a different joint admission probability.

These estimates describe creating new qualifying activity. Existing admitted unspent deposits are grandfathered; their historical TXIDs do not have to be changed. New spends of those outputs must meet the spend block's current TXID rule.
